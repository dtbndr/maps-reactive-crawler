# Offline Operator Path Workstream Slices

Agent-facing. The operator does not need to read this file.

## Objective
Connect the existing synthetic durable discovery core to a single operator-facing library and CLI, and prove the Milestone 2 connected offline exit.

## Scope
**In scope:** coordinate input, fixture-backed serial discovery, checkpoint binding, read-only status/export, cooperative cancellation, connected fresh-process acceptance and honest coverage reporting.

**Out of scope:** implementation of detail execution in this path, provider/geocoder or location input, paid calls, plugins, automatic recovery approvals, exhaustive coverage, publishing or account changes. Do not alter core frontier semantics to make the demo pass.

## Key files
- `src/index.ts`, `src/traversal.ts`: geometry, traversal and reporting contracts.
- `src/durable-state.ts`, `src/durable-discovery.ts`: transactional checkpoint, ownership, recovery and serial discovery.
- `src/operator.ts`, `src/cli.ts`: new shared operator surface and CLI adapter; export the library from `src/index.ts`.
- `package.json`: package exports and files allowlist; `test/` holds the test-only `.mjs` harness outside the production TypeScript build.
- `test/operator-*.test.mjs`, `test/fixtures/`: new synthetic contracts and process acceptance; use temporary on-disk checkpoints.
- `docs/research/bounded-crawl-recovery.md`, `docs/milestones/02-offline-reactive-slice.md`: inherited accounting and milestone boundaries.

## Architecture invariant
One serial discovery executor per writer lease; never schedule detail. Existing discovery application still atomically creates pending detail work and preserves detail provenance and gaps. Treat checkpoint and fixture as untrusted input: validate before mutations or execution, fail closed on unsupported versions, corrupt data, identity mismatch or unavailable consistent snapshot. Preserve existing no-blind-resend, retry, recovery debit, known-ID and cumulative active-time rules. No implicit unpause, recovery decision or approval. Bound checkpoints requiring manual recovery are reported, but cannot be repaired through this milestone's public API. Never classify arbitrary thrown exceptions as successful or empty observations.

## Assumptions and design decisions
- Operator contract: one operator uses one stable local checkpoint path and runs one command at a time, including inspection. No concurrent commands, network or synced mounts, or path moves while in use. The operator supplies a local filesystem supporting SQLite locking/transactions and atomic same-directory hard-link no-replace publication. These are assumptions, not runtime-certified guarantees. No separate coordination lock, native addon, or guaranteed busy result for concurrent inspection. Out-of-contract access is unsupported; SQLite errors still fail explicitly.
- A thin shared library is the only behavior owner; CLI-only was rejected because programmatic operators would diverge. A general plugin framework was rejected as unrelated to the synthetic milestone. Reopen only if the approved operator path requires another integration boundary.
- A run uses a versioned synthetic JSON fixture, SHA-256 of its exact bytes as its identity, and stable IDs, never a process-local cursor. Identical content at a different path is allowed; changed bytes fail before limit edits or execution. Create the complete initialized and fixture-bound database in a private same-directory staging location, commit and close it, then atomically publish without replacement; an interruption leaves either no destination or a complete bound checkpoint. Reject orphan sidecars and clean staging safely. Preflight validation precedes collection. Existing legacy checkpoints lacking the binding fail closed rather than being silently adopted. This assumes operator-controlled checkpoint directories and synthetic data; change of fixture format requires a version change.
- Fixture v1 is a JSON object `{version: 1, discoveries: {<workId>: {id, observationId}}, observations: {<observationId>: {result, elapsed}}}`. `workId` is the durable discovery work ID supplied by the existing send callback; `id` is the stable synthetic known ID and equals the observation lookup key `observationId`. This fixture lookup `observationId` is not the core-generated export occurrence `observationId` (`${attemptId}:observation:N`). `result` uses the existing `DiscoveryResult` shape and `elapsed` is a finite nonnegative millisecond number. All referenced IDs are nonempty strings; `id` and `observationId` must also be nonblank after trimming, consistent with durable known-ID validation. IDs are unique per work, all references resolve, unknown fields and duplicate JSON keys are rejected, and malformed data fails before mutation. Failure cases use existing result variants or explicit fixture test seams, never a cursor. A fixture missing a requested work ID fails explicitly and cannot be interpreted as empty success. Reopen the format only for a demonstrated synthetic acceptance gap.
- Before each core invocation that could start new cell submission work, select the same next cell the core would select under its recovery/running/queue rules, and verify the fixture contains its `work:${cellKey}` entry before admission, reservation, dispatch or opening a charged active interval. Do this under the writer lease against the validated immutable fixture and current traversal state; never defer lookup to `send`. The core derives this work ID in `reserveSubmission`, and may admit the queued cell before reserving, so selection must stay aligned with core behavior (factor a shared pure selector or equivalent, without changing frontier semantics). If missing, fail explicitly with no new admission, attempt, submission, active-time charge, gap or callback. A recoverable existing known-ID observation instead checks the observation by its persisted known ID and must not require a discovery entry for a new work ID; retain core recovery selection and eligibility. Existing unknown-ID reservation/dispatch and authorization refusals retain their specified behavior rather than being misclassified as fixture misses.
- Initialize with one seed, positive finite spacing in metres, explicit radius in metres or bbox in degrees, and finite independent cumulative cell, submission and active-millisecond limits accepted by the existing core. Validate using core rules; show the exact validated configuration before the first send, not an invented provider cost estimate. A preflight callback in the library runs before collection; CLI emits its JSON preflight line to stderr before invoking execution. No secrets or real data.
- `reportTraversal`'s `cells` headline is not a scheduling gate: admitted work drains subject to submission/time and recovery restrictions. A limit update does not promote blocked neighbors; report them and do not promise continuation by editing that cap. At submission or time exhaustion, eligible known-ID observation remains possible without new submission; do not suppress it. Preserve cumulative counters and retry ordinals across resumes.
- Status/export open existing SQLite read-only and use one consistent snapshot without the writer lease, initialization, recovery marking, clearing, or application writes. SQLite may require recovery or sidecar access; if a read-only consistent snapshot cannot be established, fail explicitly rather than recover or change the checkpoint. Missing, corrupt, unsupported or busy/unavailable snapshots fail explicitly. Report potentially interrupted state truthfully; never infer clean completion from absence of a writer. Inspection is supported only while no other command runs; it may fail if SQLite cannot establish a read-only snapshot. No busy result is guaranteed for out-of-contract concurrent inspection. All fields in a successful inspection must describe the same transaction snapshot.
- `start` and `resume` return promises: between completed durable operations, yield to the event loop (not merely a microtask) and check the signal before another operation or submission. This adapter passes no automatic submission or observation retry policy on any core invocation. Before each invocation under the writer lease, refuse an uncertain attempt without a known ID that carries `safeRetryAuthorization`, as a typed blocked durable outcome per the table below; do not consume, clear or rewrite the authorization. This refusal applies even though the core can consume it and send only once without a retry policy. Uncertain or dispatched unknown-ID attempts without authorization retain the core's no-blind-resend behavior, and persisted reservations retain its refusal behavior. Known-ID observation, including a persisted observation delay/authorization, remains eligible under the existing recovery and limit rules: invoke it without an automatic retry policy, preserving its normal core semantics, including consumption of a pending delay. Do not globally reject all retry-bearing checkpoints or change existing recovery APIs. After an abort, wait for any synchronous callback and its active interval to settle and close, then durably cancel while retaining the writer lease; failed settlement remains an error requiring recovery, not successful cancellation. Check an already-aborted signal before work too. Standalone `cancel` obtains the SQLite writer claim under the sequential-command assumption; interrupted cancellation is possible only after a successful claim and preserves recovery evidence. Here idle means no command is running, not the `idle` status value. It is not remote cancellation. Synchronous callbacks cannot be interrupted.
- Versioned output retains every raw occurrence and provenance, including per-observation inside/outside/unverified classification, verified identity groups and separate unverified records. Inclusive geographic eligibility applies to cell centers, not output filtering. Surface discovery and detail gaps separately, pending details, blocked/queued/running frontier, counters and all simultaneous limits alongside a headline. Exhaustion means discovery frontier exhaustion only, not coverage or detail completion. Fixture identity proves only fixture-declared identity, not provider behavior.

### Concrete surface contract
- CLI invocation is `mise exec -- node dist/cli.js <command> ...`. `start --checkpoint PATH --fixture PATH --lat N --lon N --spacing-m N (--radius-m N | --bbox SOUTH,NORTH,WEST,EAST) --cells N --submissions N --active-ms N`; `resume --checkpoint PATH --fixture PATH [--cells N] [--submissions N] [--active-ms N]`; `status --checkpoint PATH`; `export --checkpoint PATH`; `cancel --checkpoint PATH`. Exactly one area is required, all numbers parsed strictly and validated, duplicate/unknown options rejected. Every explicitly supplied resume cap must be strictly greater than its current value; omitted caps remain unchanged. Validate the fixture first and reject any equal or decreased cap atomically, without changing any caps or executing work. It does not accept geometry changes. Commands return exit 0 for a successfully reported normal/partial durable outcome, including a recovery stop after a successful writer claim; they return nonzero for invalid input, busy, corrupt, identity mismatch or unexpected failure. A live-appearing owner, including possible PID reuse, makes resume and cancel refuse the writer claim before eligibility or cancellation, with nonzero exit, empty stdout and no application mutation. On success stdout is exactly one JSON document; on failure stdout is empty and stderr contains the diagnostic (preflight may already have been emitted). No credentials.
- Exported library functions `start(options)`, `resume(options)`, `status({checkpoint})`, `exportResults({checkpoint})`, `cancel({checkpoint})` share CLI behavior. Start options contain checkpoint, fixture, geometry, limits, `onPreflight` and optional `signal`; resume contains checkpoint, fixture, optional increased limits and signal. `onPreflight` receives validated geometry and limits synchronously before collection. Status/export/cancel do not require a fixture. The CLI maps the documented flags to these objects; internal type names and test fixture values are discretionary.
- Slice B6 owns the projection, writer response lifecycle and exact JSON schema below, shared by all commands; B5 adds the CLI adapter and C adds inspection and export. Successful `start`, `resume`, and `cancel` each return exactly `{version:1, command:"start"|"resume"|"cancel", status:<status v1>}` with the actual command literal and post-operation snapshot. Capture that snapshot on the same connection after clearing this operation's writer ownership and before closing the connection; use SQLite transactions and the sequential-command assumption. Split the current combined owner removal/connection close as needed. If owner release or the consistent snapshot fails, return an error rather than a success document. Status returns the status object itself; export returns `{version:1,status:<status v1>,verifiedPlaces:[...],unverifiedObservations:[...]}`. Preflight stderr is exactly one JSON line `{version:1, type:"preflight", geometry:<geometry>, limits:<limits>}` before execution. B6 tests the complete documents, not only enums.
- Status v1 is `{version:1,state,headline,conditions,geometry,limits,counters,frontier,discoveryGaps,detailGaps,pendingDetails,coverage}`. Geometry is `{seed:{latitude,longitude},spacing,area}` with area `{type:"radius",radius}` or `{type:"bbox",south,north,west,east}`; limits are `{cells,submissions,activeTime}`; counters are `{admitted,submissions,activeTime}`. Frontier is `{queued:[cellKey],running:[cellKey],parked:[cellKey],blocked:[cellKey],discoveryExhausted:boolean}`; exhaustion means all four lists empty and no current unresolved discovery work, not absence of gaps or pending detail. Unresolved attempt statuses are `reserved`, `dispatched`, `uncertain`, and `observing`; `observed`, `skipped`, and `confirmed_no_send` are terminal. Derive current work using successor relationships: a historical uncertain attempt superseded by a successor remains as provenance but is not independently a current blocker. Do not use a raw scan of historical statuses as the exhaustion predicate. Discovery gaps are `{id:string|null,cellKey,cause,scope:"isolated"|"global"|null,status:"unresolved"|"resolved"|"skipped"|null}`; null preserves legacy absence and is treated as unresolved. Detail gaps are `{workId,identity,observationIds,status}`; pending details are `{id,identity,observationIds,status}` for every non-completed/non-skipped detail work item. Coverage is exactly `{cellCenterEligibility:true,returnedPlacesFiltered:false,exhaustive:false,detailComplete:false}`; these are limitations, not assertions that work is complete.
- An export occurrence is `{id,coordinate:{latitude,longitude}|null,classification,sourceCell,workId,attemptId,observationId,occurrence}`; absent coordinate becomes null and workId comes from the referenced attempt. Verified groups are `{canonicalKey,observations:[occurrence]}` and unverified observations are occurrences, never grouped. Preserve every raw occurrence and classification. All fields appear even when empty; sort occurrences by observationId, groups by canonicalKey, frontier by cellKey, detail work by id and observationIds lexically. Sort discovery gaps by cellKey, id, cause, scope, status; sort detail gaps by workId, identity, status, then their lexically sorted observationIds as a lexicographic sequence. Compare strings lexically and sort null before strings; identical records are interchangeable. Do not filter places.
- State precedence is `potentially_interrupted`, `cancelled`, `paused`, `idle`; successful snapshots have no `active` state. Writer acquisition must conservatively refuse an owner row whose PID appears live, including possible PID reuse; never infer staleness from the sequential-command assumption. Idle status/export may report such an owner as `potentially_interrupted` with `recovery_pending` without acquiring it; a provably dead owner is stale. Any activeInterval or recoveryPending, a live-appearing owner, or a stale owner without valid cleanPauseEvidence, selects potentially_interrupted. A stale owner with valid cleanPauseEvidence and no interval or recovery flag is paused unless cancelled; otherwise cancelled/paused flags select those states, then idle. Never clear an existing recovery flag. Bound writer acquisition applies the same stale-owner rule; preserve legacy unbound behavior.
- Conditions are sorted unique: `cells` iff blocked is nonempty; `submissions` iff submissions >= its cap; `active_time` iff activeTime >= its cap; `recovery_pending` iff recoveryPending, any activeInterval, live-appearing owner, stale owner without clean pause evidence, or the shared eligibility decision identifies a selected persisted discovery attempt that execution refuses (including `reserved` or `dispatched` without a known ID, and uncertain unknown-ID `safeRetryAuthorization` refused by the adapter; not a reservation freshly created within that invocation), or an isolated parked unknown-ID uncertainty is the only remaining discovery work and cannot run without manual recovery; paused/cancelled short-circuit persisted attempt selection as in the core, so an unselected refused attempt alone does not add this condition. Independent recovery/ownership flags and global-gap conditions remain unchanged; do not classify recoverable known-ID `dispatched`, `observing`, or `uncertain` attempts as blockers solely by status; `global_gap` iff an unresolved global discovery gap, unresolved detail gap, or reserved/dispatched/uncertain detail without a known ID blocks discovery under the core; `cancelled` and `paused` mirror flags. Headline precedence is `recovery_pending`, `global_gap`, `cancelled`, `paused`, `submissions`, `active_time`, `cells`, `discovery_exhausted`, `ready`, selecting the first applicable predicate. Caps describe reached thresholds, not a claim that known-ID observation is forbidden. `ready` never means a recovery/global blocker is runnable. `cells` means neighbors were not admitted at expansion time, not proof the cell cap caused the block: time, pause or cancellation can also block them. Test conservative refusal of a planted current/reused PID, stale dead owner with/without clean pause, orphan interval, simultaneous caps, unresolved global gap with otherwise ready work, and clean idle exhaustion. Add exact status-document tests for the planted PID with interval (`potentially_interrupted`, `recovery_pending`) and for stale ownership with genuine clean pause evidence and no interval or recovery flag (`paused`), asserting every v1 field. Add a separate exact status-document test: throw at the `reserved` boundary after persistence, let timed exception settlement close the interval and writer close, with no owner, recovery flag, gap or reached cap and the running cell's persisted reservation still present. Assert `state: "idle"`, `conditions: ["recovery_pending"]`, `headline: "recovery_pending"`, and every other v1 field and expected value; verify a subsequent invocation refuses send. Separately assert a recoverable known-ID observation is not classified as recovery-pending solely due to its attempt status and remains eligible under core rules.

- Fixture `elapsed` is validated but never charged: durable active milliseconds use only monotonic clock deltas, including active synchronous work and settlement, not inactive time between invocations. Inject a monotonic clock in library tests; control successive samples to test exact cumulative charging, no double charge, invalid/backwards samples and interrupted settlement/recovery. Production uses the existing monotonic clock.
- Expected stop outcomes must be explicit typed results or typed core stop signals, not inferred by matching exception text or by finding a limit/gap after catching an arbitrary exception. Adapt the core boundary where necessary to identify time exhaustion and unresolved recovery before/after settlement; preserve known-ID observation eligibility. Callback, clock, transition and settlement exceptions propagate as failures even if a limit or gap also exists; a failed settlement leaves its recovery marker. A successfully returned durable failed/unrecognized result may be reported as partial, but a thrown callback failure is not success.

### Pre-invocation outcomes
The shared eligibility decision runs before fixture lookup, timed core invocation or charged interval. Pending detail alone never starts discovery. Eligible known-ID observation remains a separate runnable case under core recovery and limit rules.

| Decision before invocation | Result / CLI exit |
|---|---|
| Discovery exhausted, including pending detail only; blocked-only frontier | Truthful status document / 0 |
| Paused or cancelled | Short-circuit persisted attempt selection; truthful status document / 0, retaining independent recovery and global conditions |
| Recovery pending, unresolved global gap, selected persisted reservation or refused unknown-ID safe-retry authorization, or parked-only unrunnable unknown-ID uncertainty after successful writer claim | Truthful blocked status document / 0; preserve blockers and authorization; no timed core invocation, active-time debit or sends |
| Live-appearing owner, including possible PID reuse | Refuse claim before eligibility or cancellation; diagnostic, empty stdout, no application mutation / nonzero |
| Submission or time cap reached without eligible known-ID continuation | Truthful status document / 0; preserve frontier |
| Invalid input, busy, corruption, unsupported checkpoint, fixture identity mismatch or unexpected failure | Diagnostic, no success document / nonzero |

An isolated parked uncertainty does not block other eligible discovery work. The original command whose callback throws still fails; only a subsequent successful claim can return the blocked document. No expected stop is inferred from arbitrary exceptions. Successful blocked outcomes are not permission to recover, retry or resume work.
