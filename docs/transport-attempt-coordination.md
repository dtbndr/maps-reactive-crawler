# Internal transport-attempt coordination

`coordinateTransportAttempt` is an internal building block, not provider integration or a CLI feature. Each transport attempt, including every retry, must separately pass through it. It does not coordinate cache lookup or writes. It coordinates only cooperating processes using the same operator-local directory; separate directories, installations and machines are outside its scope. It does not establish provider-policy compliance or data rights.

The wrapper holds an exclusive directory lock across the attempt and waits at least 1.1 seconds using the acquiring process's monotonic clock before starting it. Persisted wall-clock timing detects clock regression, not elapsed time. Malformed timing, clock regression and timing-write failures fail closed. A process waits up to five seconds for an existing lock, then fails rather than taking it. Long-running attempts can therefore cause another caller to fail safely.

A crash or timing failure can leave `attempt.lock` behind. Locks are never automatically stolen. Before manual recovery, the operator must verify the prior process **and its request** are no longer active, verify no other instance is running, and wait at least 1.1 seconds. Only then may the operator remove the `attempt.lock` directory. Do not delete or reset `attempt-time.json` to work around malformed timing or clock regression: resolve the clock problem and investigate the timing state first. The directory must be private to the operator and reside on a local filesystem with atomic exclusive directory creation; do not use it on a network or shared filesystem.
