# Milestone 3 — Provider and location integrations

- Implement the verified Bright Data integration and geocoder; use operator-provided credentials and redact secrets from errors and logs.
- Handle provider polling, bounded retries, rate limits and recovery according to verified contracts; document direct API notice and optional agentic MCP support.
- Perform one bounded live test only after explicit authorization and report cost and limitations.

**Exit:** offline integration tests pass and an approved live run demonstrates the intended path, or blockers are documented.

## Provisional workstream sizing

These workstreams and their order are a planning proposal, not implementation authorization or an estimate of slice count. Each workstream requires its own scope and operator-approved brief; dependencies and sizing may change as current contracts are verified. Apply the [SDLC priorities](../sdlc-priorities.md) to the first-release [happy path](../happy-path.md). Synthetic tests are credential-free and do not establish live-provider behavior.

### Workstream 1 — Bright Data discovery integration

Status: complete for the fixture-tested guarded discovery path; live behavior remains unvalidated and requires separate authorization and applicable evidence. See the [workstream brief](../workstreams/2026-11-27-bright-data-discovery/brief.md) for limitations.

Refresh the current Bright Data Maps discovery and lifecycle contracts and compare direct HTTP with the JavaScript SDK before choosing an integration. Connect the existing bounded scheduler to discovery for one confirmed coordinate seed, keyword and country as required by the verified contract, explicit geography and independent work limits. Each operator supplies their own `BRIGHT_DATA_API_KEY`; credentials are never bundled, logged or stored in checkpoints. Keep scheduling and recovery project-owned, document direct API use with notice, and retain MCP as optional agentic support rather than a runtime requirement.

Use synthetic integration tests for submission, polling, bounded failure handling and durable recovery. Preserve observation of known provider IDs and do not blindly resubmit when acceptance is uncertain or an acknowledgment is lost. Missing contract evidence blocks the affected behavior; it does not justify inventing semantics or making an unapproved probe.

**Depends on:** Milestone 2's offline path and refreshed provider evidence. **Outcome:** a fixture-tested, bounded discovery path, or documented contract blockers. **Risk:** uncertain submission, provider errors or throttling could cause duplicate paid work or hide gaps.

### Workstream 3 — live-readiness reassessment (2026-11-28 UTC)

**Outcome: documented blockers, not a live acceptance.** The connected path has synthetic evidence only; no live or paid provider request was made. No account-specific entitlement, data rights, pricing, or spending ceiling has been verified. Nothing here authorizes a demonstration.

The following must be resolved before a demonstration is proposed for approval:

- **Polling safety and observability:** [#4](https://github.com/dtbndr/maps-reactive-crawler/issues/4) and [#5](https://github.com/dtbndr/maps-reactive-crawler/issues/5) remain open. The HTTP adapter drops non-decimal `Retry-After` values, including HTTP dates, so the mapper cannot expose the unsupported-header gap. The observation loop continues immediately for non-ready progress, potentially exhausting its bounded observations while a job is running. These are material readiness blockers: limits bound local attempts, not correct provider pacing or remote job cost. Resolve them or approve an evidence-backed safe workaround separately; do not infer provider support for invented pacing.
- **Contracts and cost:** On 2026-11-28, Bright Data's [discovery contract](https://docs.brightdata.com/api-reference/scrapers/search-engines-apis/google-maps-discover-by-location) documented required country and keyword, optional `lat`/`long`, a maximum of 200 businesses per location and `limit_per_input` as a result/bill cap. The [Scraper API limits](https://docs.brightdata.com/products/scrapers/limits) document synchronous 202 with `retry-after`, 5,000 active jobs/snapshots and an IP block after 25 HTTP 429 responses within five minutes. These service-wide descriptions are not this account's quotas, a dollar cap, or a guarantee of behavior. [Public pricing](https://brightdata.com/pricing/web-scraper) cannot establish the operator's plan, minimum charges, billing units, taxes, failed/continued job charges, or remaining credit. Cost is **unknown and not bounded in currency**; even a local stop does not cancel a remote job. Confirm account-specific pricing, quotas and remote job/cancellation semantics without recording secrets before estimating spend.
- **Rights and location service:** Confirm the operator's actual provider agreement and permitted collection, retention, reuse and output rights, including applicable third-party terms; public pages are not account-specific permission or legal clearance. Bright Data legal URLs cited in the earlier research handoff returned 404 on this check, so current applicable provider terms must be located and verified. Review [Google Maps terms](https://www.google.com/help/terms_maps/) and any applicable [Google Maps Platform terms](https://cloud.google.com/maps-platform/terms) separately. For text input, the independently selected Geoapify service requires review of its [forward geocoding contract](https://apidocs.geoapify.com/docs/geocoding/forward-geocoding/), [pricing](https://www.geoapify.com/pricing/), [terms](https://www.geoapify.com/terms-and-conditions/) and applicable attribution; account limits and rights cannot be assumed. Confirmed coordinates avoid a geocoder call. The public [Nominatim policy](https://operations.osmfoundation.org/policies/nominatim/) is not authorization to use a shared default.
- **Proposed ceiling for a later approval request, not an approved run:** one operator-confirmed coordinate, one keyword and country, a small explicit radius or bounding box, at most one discovery submission/cell, a provider-side result cap if the actual request path supports and verifies it, and separately specified observation count, per-request timeout and total active-time deadline. Before approval, choose concrete geography, poll count, timeout and duration based on the verified contract and executable controls; otherwise stop. Stop on first 429, unsupported retry instruction, ambiguous submission/acknowledgment, provider error, exhausted observation or time budget, or unexpected charge/rights concern; preserve known IDs and do not automatically resubmit uncertain work. These limits do not prove a monetary bound or remotely cancel a job.

Before any spend, present a cost estimate explicitly stating any inability to bound it, the concrete work and stop limits, residual remote-job exposure and rights/contract evidence. Obtain separate explicit operator approval for a live call and for paid spend that acknowledges the uncertainty and limits; external account changes and publication each require separate approval. No credentials should be requested or included in artifacts. If approval and blockers are resolved later, record actual cost, stop reason, observed behavior and limitations; otherwise this blocker record is the milestone outcome, not live validation.
