## Discovery request and output

**Documented facts:** The catalog's `discover_by_location` schema has required `country` and `keyword`; optional `lat`, `long`, and `zoom_level` numeric inputs are shown. Its declared output field is `url`. The sample input uses country `IN`, a keyword/address-like phrase, coordinates and zoom 14; that is an example, not a project default or tested result. The catalog does not define an explicit radius or bounding box input. The project still requires operator-supplied coordinates and an explicit area bound, regardless of provider optionality; do not invent a country or silently substitute a location. Determine and validate an appropriate country value from the operator's input and verified contract before integration.

The catalog's discovery **URL** output is not itself proof of a place record, stable place identifier, name, coordinates, nor of full information being returned by a discovery call. The catalog's separate `collect_by_url` method accepts a required `url` and declares many fields, including `place_id`, `name`, `address`, `lat`, `lon`, `rating`, `reviews_count`, `country`, category and business/contact details. A declared output field does not establish it is always populated. `place_id`, latitude/longitude completeness, response envelope, duplicate behavior and detail coverage are not guaranteed by this catalog declaration.

**Inference for the happy path:** Treat a discovery result as a candidate URL, not a deduplicated place. The documented method mapping is location discovery → URL candidate(s) → optional/conditional `collect_by_url` for place details. If this project requires provider-produced place IDs and coordinates for persistence, deduplication, export or coordinate-based filtering, a detail-collection stage is needed unless another verified source supplies those fields. Discovery URLs alone may suffice to decide whether raw discovery output is nonempty and trigger the project's deterministic expansion rule, but the actual run-result shape and whether it contains one URL per place remain unverified.

**Detail necessity:** **Conditional**, not proven necessary for every search. Detail is not shown as necessary to ask for location discovery or to observe a nonempty discovery output; it is conditionally needed for the intended place-record contract when discovery output does not supply required IDs/coordinates/fields. If raw output count controls expansion, a provider cap or truncated result set can change fan-out and coverage independently of details. A successful empty result and a failed/partial result must remain distinct; public catalog fields do not settle this behavior. Do not imply exhaustive Maps coverage, reliable coordinate availability, or complete results.

## MCP versus direct API

The MCP tool reference documents `search_scrapers` (catalog discovery), `get_scraper_details` (method schema/details), `run_scraper` (execute method on inputs; waits up to 45 seconds, then may return a snapshot ID), `get_scraper_progress`, and `get_scraper_results`. It says scraper runs are billed per record. This maps agent assistance onto the same scraper and methods, not a separate Maps data contract. The README also documents catalog refresh and configurable tool groups; the actual advertised inventory depends on server version and configuration. MCP support is useful for agentic discovery and inspection, but is not required in the crawler runtime.

Direct API operation-specific pages cover the location discovery and URL collection methods. The catalog is the evidence in this handoff for inputs/output fields, but no live call was made to compare a runtime payload. An integration should pin/check the provider contract and compare actual API versus MCP behavior only after the operator authorizes any potentially billable probe. Keep the deterministic single-seed scheduler, bounds, work limits, persistence, deduplication, errors, cancellation/resume and stop reasons project-owned. Do not make the MCP server an LLM-controlled scheduler or a runtime prerequisite. Direct API use is permitted with notice.

## Legacy trigger parameters: status unresolved

The first legacy reference `backend/src/services/maps.js` constructs input records by mapping `{ lat, lon, zoom }` to `{ lat, long, zoom_level, keyword, country }`; its source URL appends `type=discover_new&discover_by=location` to `/datasets/v3/trigger`. The separate archived reference `packages/backend-legacy/src/services/maps.ts` also appends those same query values. This is verified historical source behavior in both inspected trees, not confirmation of a current provider requirement. The current catalog names the method `discover_by_location`, while its contract record describes inputs/outputs and does not establish those two legacy query parameters as required. The current operation pages use their public `google-maps-discover-by-location` naming, but this research did not verify a complete request example proving whether the query flags are required, optional compatibility parameters, or legacy artifacts. **Explicit unknown:** their current requirement/acceptance status. Do not carry them forward as a requirement or remove them based only on the name. Next step: use current versioned API request examples/contract or obtain provider confirmation, then any probe requires separate operator approval. No value or parameter has been invented here.

## Acceptance gap review (documentation red → green)

**Before research (RED / acceptance gap):** The preceding handoff did not establish country and keyword requirements alongside the coordinate-driven project constraint; did not clearly compare inputs and outputs by method; did not distinguish discovery URLs from place records or state detail necessity; and left current source locations, direct-API mapping and the legacy trigger parameters unresolved. These are acceptance gaps, not failing software tests; this documentation-only slice uses the brief's prescribed gap review in place of a code test.

**After research (GREEN / acceptance review):** Country, keyword, coordinates and zoom are compared with explicit required/optional status and the project coordinate/bounds constraints; catalog discovery output and detail output are separated; detail necessity is classified conditional; MCP and direct API paths are compared; primary source URLs and access date are recorded; legacy params are explicitly blocked as unknown with a next step. No provider-runtime/result-shape or paid-use claim has been silently promoted to fact. Remaining gaps are explicit blockers for contract completion, not unacknowledged acceptance misses.
