## Discovery request and output

**Documented facts:** The catalog's `discover_by_location` schema has required `country` and `keyword`; optional `lat`, `long`, and `zoom_level` numeric inputs are shown. Its declared output field is `url`. The sample input uses country `IN`, a keyword/address-like phrase, coordinates and zoom 14; that is an example, not a project default or tested result. The catalog does not define an explicit radius or bounding box input. The project still requires operator-supplied coordinates and an explicit area bound, regardless of provider optionality; do not invent a country or silently substitute a location. Determine and validate an appropriate country value from the operator's input and verified contract before integration.

The catalog's discovery **URL** output is not itself proof of a place record, stable place identifier, name, coordinates, nor of full information being returned by a discovery call. The catalog's separate `collect_by_url` method accepts a required `url` and declares many fields, including `place_id`, `name`, `address`, `lat`, `lon`, `rating`, `reviews_count`, `country`, category and business/contact details. A declared output field does not establish it is always populated. `place_id`, latitude/longitude completeness, response envelope, duplicate behavior and detail coverage are not guaranteed by this catalog declaration.

**Inference for the happy path:** Treat a discovery result as a candidate URL, not a deduplicated place. The documented method mapping is location discovery → URL candidate(s) → optional/conditional `collect_by_url` for place details. If this project requires provider-produced place IDs and coordinates for persistence, deduplication, export or coordinate-based filtering, a detail-collection stage is needed unless another verified source supplies those fields. Discovery URLs alone may suffice to decide whether raw discovery output is nonempty and trigger the project's deterministic expansion rule, but the actual run-result shape and whether it contains one URL per place remain unverified.

**Detail necessity:** **Conditional**, not proven necessary for every search. Detail is not shown as necessary to ask for location discovery or to observe a nonempty discovery output; it is conditionally needed for the intended place-record contract when discovery output does not supply required IDs/coordinates/fields. If raw output count controls expansion, a provider cap or truncated result set can change fan-out and coverage independently of details. A successful empty result and a failed/partial result must remain distinct; public catalog fields do not settle this behavior. Do not imply exhaustive Maps coverage, reliable coordinate availability, or complete results.

### Lifecycle acceptance evidence and gaps

The acceptance evidence missing before this investigation (documentation RED) was: an end-to-end trigger/acknowledgment contract; durable snapshot/run identifier shape; complete state transition and terminal-state meanings; polling cadence/timeout rules; result retrieval, pagination, and retention; cancellation operation and semantics; error/partial/empty distinctions; and whether documented pricing or limits distinguish discovery from detail. The source inventory above does not close all these gaps.

**Documented MCP facts:** `run_scraper` runs a scraper method on a list of inputs, waits up to 45 seconds, and may return a snapshot ID if still running; its description says runs are billed per record. `get_scraper_progress` reports `starting`, `running`, `ready`, `failed`, or `canceled`. `get_scraper_results` returns records of a finished run. This is the public MCP tool description, not a verified runtime state machine or guarantee that every run follows these transitions. It does not specify the snapshot ID format, whether an ID is returned on every path, or a durable request correlation key.

The general Scraper API limits page documents that a synchronous `/scrape` request still running after one minute returns HTTP 202 with a `snapshot_id`; its `retry-after` header says how long to wait before polling (10 seconds in that page's example, not a universal polling interval). For asynchronous `/trigger`, the page documents a 1 GB input-data limit per job. It lists a 5,000 active jobs/snapshots limit; new requests return HTTP 429 when that dataset-level limit is reached. It also states 25 HTTP 429 responses per IP within five minutes trigger a temporary IP block on every API request, which expires after one hour. These are general Scraper API limits, not verified Maps-specific or MCP limits.

The same page documents 30-day snapshot retention after job completion; snapshot downloads are limited to 5 GB per request, with larger snapshots downloadable in parts using `batch_size` and `part`, and a minimum part `batch_size` of 1,000 records. These direct API download details do not establish MCP result pagination or identical MCP behavior.

**Still not documented in the checked sources / unknown:** the mapping between MCP status and direct API statuses; whether `ready` can mean zero records or partial output; how partial records are signaled; per-record failures; cancellation request/tool/endpoint, race behavior, or billing on cancellation; snapshot lookup after expiry; retry guarantees; and whether each Maps method has additional caps or method-specific throttling. The limits page lists HTTP 400 for too few inputs on scrapers whose minimum input count applies, but does not say which Maps methods use such a minimum. The MCP tool list has a progress check and results retrieval but no named cancellation tool. This does not prove cancellation is unavailable over other interfaces. Do not model failure as empty success or assume all ready snapshots are complete.

### Rate limits, other limits, and polling assumption check

The general [Scraper API limits](https://docs.brightdata.com/products/scrapers/limits) reference (checked 2026-11-12) documents the following limits and throttling behavior:

- **Concurrent active work:** at 5,000 active jobs or snapshots per dataset, new `/trigger` and `/scrape` requests return HTTP 429. The published table does not give a Maps-specific lower limit or account override.
- **429 rate / temporary IP block:** 25 HTTP 429 responses from an IP within five minutes cause Bright Data to block that IP on every API request for one hour. This is an explicit provider-documented throttle consequence, not a per-minute request quota. The exact condition producing an individual 429 can include the active-job cap above.
- **Async input:** `/trigger` input data is limited to 1 GB per job. The page recommends one bulk job over starting one job per input to stay under the active-job cap; do not interpret that as a required batching design.
- **Sync wait and polling hint:** `/scrape` waits one minute; if the request is still running it returns HTTP 202 and `snapshot_id`. The page says the `retry-after` header gives the wait before polling and gives 10 seconds as the value “at the time of writing.” That is an example, not a fixed poll interval. This direct API behavior is distinct from the MCP description's up-to-45-second wait.
- **Snapshot access:** snapshots are retained for 30 days after job completion. A download request is limited to 5 GB; larger results can be downloaded in parts using `batch_size` and `part`, with a minimum `batch_size` of 1,000 records.

These are general Scraper API service limits; the public page does not establish whether Maps has additional caps, whether MCP has identical throttling, any guaranteed throughput per second, or account-specific overrides. Treat the stated general limits as documented ceilings/429 behavior, not as a safe operating target. The scraper catalog does not publish a Maps-specific maximum geography. MCP `search_engine_batch`/`scrape_batch` limits (up to five) apply to those distinct tools, not evidence of a scraper-run batch limit.

The MCP reference's 45-second wait is not a requirement to wait 45 seconds before polling. I found no support in the checked sources for the legacy five-minute initial wait or 30-minute polling cap. Treat both as historical client implementation choices, not current Bright Data requirements; their origin/appropriateness remains unknown. Direct API `/scrape` does document a one-minute synchronous wait and a `retry-after` header after HTTP 202, but this does not validate the legacy values or prove the MCP tool follows that cadence.

**Inference / downstream risk:** reactive fan-out can reach the active-job cap or 429/IP-block condition, especially if a client launches many jobs independently; blindly retrying 429s during the documented block window can prolong failure. A single-seed expansion algorithm can under-expand if output is capped/truncated, and overstate completion if incomplete output is treated as complete. Explicit local call, cell, elapsed-time and area bounds remain necessary. The 1 GB request limit and 5 GB download limit do not themselves establish place-count completeness. Any runtime validation or paid probe requires separate operator approval.

### Duplicate-paid-request crash windows and idempotency

A client can submit a scraper run and lose the response before it durably saves the returned snapshot ID (or crash while the MCP run call is waiting up to 45 seconds). The provider may have accepted and started the job even though the client has no identifier. A restart that blindly submits again can therefore create a second run and duplicate work/charges. Similar ambiguity exists after receiving an ID but before persisting it; after a timeout/network error whose acceptance status is unknown; and when a poll/result request fails locally and the client mistakes that for a run failure and re-submits. Discovery-to-detail fan-out can also repeat detail submissions if progress is not durably recorded, though no billing behavior for these cases is documented.

The checked public references do **not** document an idempotency key for scraper submission, an exactly-once guarantee, a lookup by client-supplied request key/input, duplicate suppression, or billing adjustments for duplicate submissions. MCP snapshot IDs enable follow-up once obtained, but no source here says they can recover a lost acknowledgment. This is an explicit contract unknown, not proof that idempotency or support-side lookup is absent. Do not select a retry/recovery policy in this research. It is a P0/P1 integration risk for safe resumability and budget control: before paid integration, verify idempotency/lookup and charge behavior from current authoritative provider terms/API docs, or bring the unresolved risk and an approval-gated non-production probe plan to the operator. No such probe is authorized here.

### Empty, failed, partial, and capped results

- **Empty:** the sources do not state whether successful zero-result runs return an empty list, omit output, or have a distinct status; a zero-record bill rule is also unspecified. Empty must not be inferred from a timeout, missing response, failed state, or absent snapshot.
- **Failed:** MCP lists `failed` as a progress state but does not define its error payload, retryability, partial-result availability, or billing.
- **Partial:** no checked source defines a partial state, per-input success/error mapping, or how partial results are marked. Retrieval is described for a finished run only; that does not settle whether failed/canceled runs retain partial records.
- **Capped/truncated:** no Maps-specific cap, truncation marker, cursor, or pagination contract was found in the checked material. No evidence supports treating a returned set as complete. This affects both place coverage and reactive expansion.

These distinctions are provider-contract unknowns. Preserve separate states in any eventual adapter and do not call an unverified payload empty/complete. Resolve before claiming resumability, completeness, or cost bounds.
