# Location-input geocoder evaluation

## Follow-up: individual-operator model and Nominatim policy

The owner intends the open-source tool for individual operators, who are responsible for their own provider usage; the project does not guarantee service availability. No centrally operated coordination service is planned. Place-name lookup must not silently default the country: disable lookup with an explanatory message when country is missing. Present candidates for explicit confirmation rather than silently selecting the first result. These are design decisions, not implemented behavior.

The owner agreed to serialize ordinary interactive requests and space them at least 1.1 seconds apart, including retries, with caching and no autocomplete. This local safeguard is not an application-wide limit. The [OSMF Nominatim usage policy](https://operations.osmfoundation.org/policies/nominatim/) states that limits apply per website/application and the sum of traffic by all users must not exceed them. It permits directly user-triggered searches provided the number of users is moderate; independent installations cannot enforce the aggregate ceiling with local limiters alone. Operator responsibility does not change provider policy or guarantee compliance. Recheck the policy before implementation.

**Owner decision:** Treat each installation as an independently operated individual tool, not a project-operated shared geocoding service. Operators choose their service and are responsible for their usage and data obligations. Provide policy guidance, attribution and the agreed safeguards, but do not block project progress on an aggregate-traffic guarantee or a legal determination for every operator's exports. Nominatim may throttle or deny access. No provider integration has been implemented or runtime-tested.

The public-service policy also requires identification and attribution, prohibits autocomplete, requires service switching without a software update, and imposes additional restrictions on bulk and periodic scripts. Design attribution and data handling for the actual fields and workflow; do not represent the owner's responsibility decision as a grant of rights. The historical recommendation gates and calls for aggregate confirmation or individual export-rights determinations below are superseded by this owner decision. The policy's explicit per-application wording above supersedes any historical suggestion that it specifies no application-wide scope.

## Initial documentation-only red check (before research)

At the start of this investigation, the repository and first-release description did not contain evidence sufficient to accept any geocoder. Specifically missing were:

- **Intended use/workload:** explicit supported operator workflow and expected number of geocoding requests per installation, operator, and all users combined.
- **Free eligibility:** current pricing, eligibility for this public open-source tool and its operators, and whether use is free at the expected volume.
- **Applicable policy:** provider terms, acceptable-use policy, service-specific restrictions, and whether deployment/use by independent operators is allowed.
- **Quotas and rate-limit scope:** per-key/account/IP/application limits and aggregate limits across operators or the shared public service; burst and sustained limits.
- **Authentication:** whether a key/account is required, how credentials may be supplied, and restrictions on client-side/public distribution.
- **Ambiguity:** multiple-match behavior, confidence/relevance evidence, and whether results can be presented for explicit operator confirmation instead of guessing.
- **Country:** supported country filters, country-code convention, language/locale behavior, and absence of a silent US default.
- **Attribution:** required wording, display placement, and whether CLI/export-only output satisfies the requirement.
- **Storage and rights:** caching/retention and reuse rules for query and result data, applicable source-data/database rights, and limits on redistribution/export.

This is the documentation-only RED state: no candidate has demonstrated all of the acceptance evidence. This slice does not add code tests because its artifact is a research comparison and no resolver implementation exists; evidence is checked against the criteria below instead.

## Workload and assumptions to confirm

**Provisional workload model (inference, not measured):** one operator provides one coordinate or human-readable place to seed a bounded crawl. A place seed should require one forward-geocoding operation; retries, disambiguation, and operator edits add requests. Crawls may be run repeatedly. The crawler can be installed by many independent operators, so there is no defensible assumption that aggregate traffic is limited to one developer or one installation. The project should not silently multiplex operators through a shared service.

**Unknown operator behavior:** installation count, concurrent use, geocoding frequency, retry behavior, automated/batch use, and whether operators will configure their own key are not established. No free-tier or public-instance quota is accepted until its scope can accommodate the intended aggregate workload or a per-operator-key design is approved. Owner confirmation is required for workload and credential model.

## Evaluation criteria

A candidate can be recommended only when current authoritative evidence supports all first-release requirements:

1. Use is permitted for this operator-run software and eligible at no charge for the declared workload; free tier is not equivalent to permission or sufficient shared capacity.
2. Applicable policy and rate limits are explicit, including aggregate scope, and a compliant request/retry model can be stated.
3. Authentication and independent-operator credential handling fit the CLI without embedding a shared secret.
4. Results support explicit country context and language as appropriate; no country is silently inferred as US.
5. Ambiguous or low-confidence results can be surfaced for operator choice; no result is silently treated as a definitive location.
6. Attribution can be met in CLI and exported documentation/output.
7. Caching, retention, derived data, export, and source-data/database rights permit the planned checkpoint and result workflow.
8. Provider service availability and geocoder coverage are suitable enough for the first-release happy path, with failure and unsupported-location behavior documented.

P0/P1 focus: policy/eligibility, aggregate limits, unsafe silent location choice, credentials, and rights could block a safe first release (P0/P1 depending on evidence and workaround). Language/coverage gaps may be P1 where they prevent correct location input; cosmetic output preferences are lower priority. This is evaluation sequencing, not a priority regrade of implementation tasks.

### Location-input contract for subsequent design

This is a provider-neutral operator-safety handoff, not an implemented, provider-specific, or runtime-tested contract. It defines only what can be justified without assuming response fields or country behavior from an unselected provider.

**Common rules**

- Require the operator to choose a seed path: confirmed coordinates or text to resolve. Do not silently switch paths, pick a text result, or default country to the United States.
- Before a crawl starts, show the effective seed location and country context and require an explicit confirmation. A later change invalidates that confirmation and requires reconfirmation.
- Require explicit country input for place-name lookup, even if the provider makes it optional; disable lookup with an explanatory message if missing. For coordinates, collect country when the downstream provider requires it. Validate and normalize according to the relevant provider's documented convention. Never infer country from locale, IP address, coordinates, language, or provider defaults.
- Preserve the distinction between an operator-supplied country context and a provider-reported candidate country. Do not silently rewrite one to match the other.

**Confirmed-coordinate path**

- Accept one latitude/longitude pair in that order. Latitude must be a finite number from -90 through 90 inclusive; longitude must be a finite number from -180 through 180 inclusive. Reject missing components, extra components, malformed numeric text, NaN, infinities, and out-of-range values with an actionable validation error; do not coerce malformed values into coordinates. These are geographic coordinate-domain bounds, not provider-specific guarantees.
- Display the normalized pair in the documented order and its explicitly supplied country context; ask the operator to confirm before crawl start. Do not reverse-geocode or forward-geocode this path: the coordinates are the seed and geocoding is bypassed.
- If provider/project requirements need a country for later search, collect and validate that country explicitly even though coordinates were supplied. Coordinates alone do not prove which country the operator intends. This path has no resolved-candidate country to compare, and this contract does not call a reverse-geocoder to manufacture one. If the operator knows the stated country conflicts with the intended point, require correction or explicit resolution before confirmation; if a later authoritative boundary check detects a mismatch, stop and present it for operator resolution rather than silently changing the country. Automated point-in-country validation is unresolved and must not be claimed without an approved source and behavior.

**Human-readable text path**

- Require non-empty operator text and explicit country context; never add an implicit US value. Send country as a provider-supported country filter when documented. If the selected provider supports only a bias, disclose that it is a preference rather than a restriction; do not represent it as a guaranteed country constraint. If neither behavior is documented, the provider is not usable for this contract until its behavior is established.
- Present provider-returned candidates for operator choice, showing only fields documented by the selected provider and useful to distinguish results (at minimum the returned location label and country when available). Do not invent confidence scores, response shapes, or a uniqueness threshold. Even a single candidate is shown for confirmation; never auto-select.
- On zero candidates, report no result and let the operator revise input/country or cancel. On multiple candidates, require an explicit choice or revised query; do not rank-and-pick silently. On provider/network/rate-limit errors, show a non-secret actionable failure and permit retry only within verified limits; do not treat failure as no result or start a crawl.
- Compare the operator's requested country context with the candidate's provider-reported country when both are available. If they differ, stop for an explicit choice to revise country/query or cancel; do not silently accept a cross-country result or rewrite the requested country.
